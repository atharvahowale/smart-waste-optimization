Build a polished, interactive web prototype for our SIH 2026 project:

PROJECT TITLE:
Smart Plastic Waste Collection Optimization Platform

CORE PURPOSE:
This is NOT a generic recycling dashboard.

The prototype must demonstrate our mathematical route-optimization model working in real time.

The most important part of the prototype is the MATHEMATICAL DECISION ENGINE.

The UI should make it visually obvious WHY a collection point was selected, which points were rejected, how the vehicle's remaining capacity changes, and how the route is re-optimized after actual collection data or live point updates.

The prototype should feel like a real operational optimization system rather than a static mockup.

--------------------------------------------------
1. CORE ALGORITHM
--------------------------------------------------

The complete decision loop is:

FILTER → SCORE → SELECT → COLLECT → VERIFY → UPDATE → RE-OPTIMIZE → REPEAT

At every decision:

1. Receive latest collection-point data.
2. Filter invalid/infeasible collection points.
3. Calculate score for every feasible point.
4. Select the highest-scoring feasible point.
5. Vehicle travels to that point.
6. At checkpoint, replace estimated quantity with actual collected weight and volume.
7. Update vehicle state.
8. Recalculate remaining weight and volume capacity.
9. Recalculate scores.
10. Continue until no feasible collection points remain or vehicle capacity is exhausted.

This loop must actually execute in the prototype.

DO NOT fake the mathematical result with hardcoded "recommended point" labels.

The selected point MUST be calculated by the algorithm.

--------------------------------------------------
2. VEHICLE STATE
--------------------------------------------------

Each vehicle has:

- Maximum weight capacity W_max
- Maximum volume capacity V_max
- Current loaded weight W_load
- Current occupied volume V_load
- Current location L_v

Remaining capacity is:

W_rem = W_max - W_load

V_rem = V_max - V_load

Display these values prominently in the UI.

Example:

Maximum:
500 kg | 10 m³

Current:
220 kg | 6 m³

Remaining:
280 kg | 4 m³

Show live progress bars for both weight and volume.

These values must change after every collection.

--------------------------------------------------
4. FEASIBILITY ENGINE
--------------------------------------------------

Before scoring, remove points that are not feasible.

A point is feasible only if:

S_i = 1

AND

W_hat_i <= W_rem

AND

V_hat_i <= V_rem

AND

A_i = 1

Where:

S_i = availability status

A_i = accessibility status

W_hat_i = estimated weight

V_hat_i = estimated volume

The prototype MUST visibly show this filtering.

For every point, show:

AVAILABLE / UNAVAILABLE
WEIGHT FIT / OVER CAPACITY
VOLUME FIT / OVER CAPACITY
ACCESSIBLE / INACCESSIBLE

Then show:

FEASIBLE
or
REJECTED

Example:

P3:
Available ✓
Accessible ✓
Weight: 300 kg > 280 kg ✕
Volume: 4.5 m³ > 4 m³ ✕
STATUS: REJECTED

Do not calculate a score for rejected points.

Create a visible "Feasible Set":

F = {P1, P2, P5}

This is important because the prototype must demonstrate the mathematical constraint layer.

--------------------------------------------------
5. POINT SCORING ENGINE
--------------------------------------------------

THIS FORMULA IS CRITICAL.

DO NOT MODIFY, SIMPLIFY, REPLACE OR APPROXIMATE IT.

Use exactly:

Score_i =
α(W_hat_i / W_rem)
+ β(V_hat_i / V_rem)
- γ(D_i / D_max)
- δ(T_i / T_max)

Render the formula beautifully using MathJax or KaTeX.

The formula must be used by the actual JavaScript/TypeScript calculation engine.

Definitions:

Score_i:
Final score of collection point i

W_hat_i:
Estimated plastic weight at point i

W_rem:
Vehicle's remaining weight capacity

V_hat_i:
Estimated plastic volume at point i

V_rem:
Vehicle's remaining volume capacity

D_i:
Distance from current vehicle position to point i

D_max:
Maximum/reference distance used for normalization

T_i:
Estimated travel time to point i

T_max:
Maximum/reference travel time used for normalization

α:
Weight-utilization priority

β:
Volume-utilization priority

γ:
Distance penalty

δ:
Travel-time penalty

i:
Collection-point index

The coefficients must be configurable in the UI.

Example default values:

α = 0.30
β = 0.30
γ = 0.20
δ = 0.20

Ensure:

α + β + γ + δ = 1

Provide sliders or numeric controls for these four parameters.

If the user changes α, β, γ or δ, ALL feasible-point scores must recalculate immediately.

--------------------------------------------------
6. NORMALIZATION
--------------------------------------------------

The scoring formula uses normalized quantities.

Weight utilization:

W_hat_i / W_rem

Volume utilization:

V_hat_i / V_rem

Distance:

D_i / D_max

Travel time:

T_i / T_max

Calculate D_max and T_max from the current candidate set/reference values.

Do not use raw kilograms, kilometres and minutes directly in the score.

The purpose is to make all terms dimensionless and comparable.

11. RE-OPTIMIZATION
--------------------------------------------------

THIS IS ONE OF THE MOST IMPORTANT FEATURES.

After every checkpoint:

DO NOT continue using the old route.

Instead:

1. Update current vehicle location.
2. Update actual weight.
3. Update actual volume.
4. Recalculate remaining capacity.
5. Rebuild feasible set.
6. Recalculate distance and travel time.
7. Recalculate Score_i.
8. Rank all feasible points again.
9. Select the new highest-scoring point.

Display a visible event:

"VEHICLE STATE CHANGED"

then:

"RECALCULATING FEASIBLE SET..."

then:

"RECALCULATING SCORES..."

then:

"NEW BEST NEXT POINT → P?"

Use a short animation so the user can see the optimization cycle happening.
